Anatomy of a foreman release

Follow one release — v0.2.1 — from your keyboard to a user's restarted app, and learn the three invariants that decide whether any change to this system is safe.

The single mental model

Everything in the spec is one pipeline with one producer, one source of truth, and several consumers that deliberately know as little as possible:

1 · YouEdit Cargo.toml to 0.2.1, commit, push tag v0.2.1.
2 · CIChecks tag == Cargo.toml, runs cargo test, builds release, zips, checksums, publishes a GitHub Release.
3 · The ReleaseNow is releases/latest. Immutable. Every consumer below reads only this.
4a · New userirm …/install.ps1 | iex → verify → extract → PATH. Installed.
4b · Existing userRunning foreman's 6-hourly check sees 0.2.1 > 0.2.0 → quiet chip ↓ v0.2.1.
5 · Click(Phase 4) download → verify → rename-swap → "Restart to update" → user restarts on their schedule; cold restore rebuilds the workspace.

Notice what does not exist: no update server, no manifest file, no version database. The GitHub Release object is the manifest. This passed the review's deletion test: if we built a custom manifest and then deleted it, nothing would be lost — it would be a pass-through over data GitHub already serves. Modules that fail the deletion test don't get built.

The three invariants

Every future PR against this system — yours or an agent's — is safe or dangerous depending on whether it preserves these:

1. Version truth lives in Cargo.toml; the tag must agree

Two places could claim to know the version (file and tag), so CI makes disagreement impossible: mismatch = no release. One fact, one owner, mechanically enforced. When something reports the wrong version, you know exactly where truth lives.

2. CI is the only writer of asset names; consumers match suffixes

The name foreman-v0.2.1-x86_64-windows.zip is spelled in one place: release.yml. The install script and the updater never rebuild that string from a version — they scan the release's asset list for ends-with -x86_64-windows.zip (select_asset(), pure, unit-tested). A rename typo therefore breaks one writer, not three consumers on tag day.

3. The swap exists in exactly one language

Windows won't let you delete or overwrite a running exe — but it will let you rename one (how rustup updates itself; verified empirically on this machine during the design fact-check). So the updater renames the running foreman.exe → foreman.exe.old and slides the new exe into place. That dance is subtle (rollback, AV interference, .old cleanup), so it lives only in src/update.rs. The install script refuses to touch a running foreman rather than re-implement it in PowerShell.

Why the one-liner beats SmartScreen SmartScreen only screens files carrying Mark-of-the-Web — a hidden Zone.Identifier stream browsers attach to downloads. Invoke-WebRequest doesn't write it and Expand-Archive doesn't propagate it, so a script-installed foreman.exe has no MotW and launches clean, unsigned. But Explorer's built-in zip extraction does propagate MotW — a browser-downloaded, Explorer-extracted portable zip still hits the scary dialog. Details: Outflank's MotW analysis.

Where the risk was moved

Two review decisions shaped the plan's risk profile, and you'll see them in the phasing: the updater ships notify-only first (Phase 3 — chip links to the Releases page) and gains one-click apply in Phase 4 only after a real v0.2.x release cycle proves the loop. The swap is the most dangerous code in the app — it now sits behind evidence instead of ahead of it. And the Inno installer was deferred entirely: two installers writing the same layout meant silent drift, so until someone asks for a setup.exe, the script and zip are the only writers.
