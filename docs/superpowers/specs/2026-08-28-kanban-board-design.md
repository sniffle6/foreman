# Kanban board — design spec

Settled with the user 2026-08-28. Builds on the brainstorm record
(`2026-08-28-kanban-board-brainstorm.md` in this directory), which holds the
foundational decisions and their whys: board = work-in-flight only, in-repo
file-per-card storage, all writes through the pipe, workers are dispatched
Sessions (not subagents), three-tier agent education, and the v1 scope fences
(fixed columns, no drag-and-drop, one prompt template, no card editor). Those
are not re-argued here; this spec designs what the brainstorm left open.

## Card schema

One file per card: `.foreman/tasks/<id>.json`. Written only by the app; read
by anyone.

```json
{
  "v": 1,
  "id": "a3f8k2",
  "title": "Fix resize flicker",
  "body": "optional longer description, plain text",
  "state": "backlog | in_progress | blocked | done",
  "blocked_reason": "only present when blocked",
  "claim": {
    "terminal": "t4",
    "run": "uuid of the app instance that wrote the claim",
    "agent": "claude",
    "at": "2026-08-28T14:03:00Z"
  },
  "created": "2026-08-28T13:55:00Z",
  "updated": "2026-08-28T14:03:00Z"
}
```

- **Id: short random base36**, generated by the app, collision-checked at
  create (single writer, so regenerate on hit). Random because two branches
  must be able to create cards independently and merge without colliding —
  sequential ids reintroduce exactly the conflict file-per-card storage was
  chosen to avoid. Short enough to type by hand in a close-out command.
  *Rejected:* sequential ids (cross-branch collisions); UUIDs (untypeable).
- **`v` is per card file.** A branch can carry old- and new-version cards at
  once and each file explains itself. *Rejected:* a directory-level marker
  file (one more merge surface that versions nothing by itself); a README in
  `.foreman/` (doc-drift bait in a data directory).
- **`body` is a pointer, not a spec.** Free-form plain text, interpolated
  verbatim into the dispatch prompt. Convention (taught by the foreman-kanban
  skill, not enforced): a few lines of task statement plus paths and issue
  numbers. The worker is a full Session sitting in the repo — it can read the
  docs the body points at. Durable content belongs in GitHub Issues or
  `docs/`, per the routing rule in the brainstorm record. *Rejected:* pasting
  full context into the body (forks the source doc silently, and multi-line
  JSON strings diff and merge badly).
- **`claim` records the card↔Session link at claim time**: the worker's
  terminal id, the dispatching app instance's run nonce, which agent binary
  was dispatched, and when. Present only while the card is claimed; cleared
  by close-out and release transitions.

### Orphan detection is derived, never stored

The app generates a run nonce (UUID) at startup. A card is **orphaned** iff
its state is in-progress and any of: the claim is missing, the claim's run
nonce is not the current run's, the claimed terminal no longer exists, or the
claimed terminal has exited (Sessions whose child died stay visible in an
exited state — the same signal `foreman status` reports and chat presence
reconciles on, see `src/chat.rs` `reconcile`).

Derived beats stored because a stored flag can lie: the app can die before
writing it, and a branch switch can restore a card file whose flag describes
last week. The derived check is recomputed at render time and cannot go
stale, and it makes restart and branch-switch reconciliation cost zero file
writes. Accepted cost: orphaned-ness is not visible by reading the JSON file
alone — only on the board or via `foreman kanban list`.
*Rejected:* writing an orphaned flag into the card file.

## Reconciliation

The cases that would otherwise each leave a zombie card. All of them fall out
of the derived-orphan rule plus "files are authoritative over memory".

1. **User closes the worker terminal.** The claimed terminal is gone; the
   card renders orphaned immediately. No file write.
2. **Agent crashes, or exits without closing out.** The pane survives in an
   exited state, the claim's terminal reports exited, the card renders
   orphaned. This also catches the quiet failure: an agent that finishes but
   forgets its close-out command flags instead of squatting.
3. **Foreman restarts.** New run nonce; every claim stamped by the previous
   run fails the nonce check, so all previously in-progress cards render
   orphaned. No startup sweep, no writes. (Sessions do not survive a restart,
   so this is always the truth.)
4. **Branch switch or pull rewrites `.foreman/tasks/`.** The board re-reads
   after its own writes and via a cheap directory-staleness poll (on the
   order of seconds) while the board window is visible. A card file that
   vanished drops off the board; the worker Session is never killed by this.
   If the file comes back (switching back to the branch), the card
   rehydrates, and if its run nonce and terminal still check out the claim is
   simply valid again — no flag flapping.

Close-out verbs on a missing card file **error, never create** — a card is
never resurrected by its own close-out. The agent sees the error in its
terminal; the human sees an orphan-free board that simply lacks the card.

Human recovery from an orphaned card, from the board: **re-dispatch** (a new
claim overwrites the dead one) or **send back to Backlog** (the release
transition, clears the claim).

## Verb surface

All verbs ride the pipe (`\\.\pipe\foreman`); the app is the single writer
and validates every transition, rejecting garbage with a clean error.

| Verb | Effect |
|---|---|
| `foreman kanban add <title> [--body B]` | Create card in Backlog; prints the new id (an orchestrator captures it for `wait`) |
| `foreman kanban list [--state S] [--json]` | Human-readable lines, or one JSON card per line for agents; both include the derived orphan flag (it exists nowhere in the files) |
| `foreman kanban start <id>` | Claim + move to In Progress; claimant is the caller's own `FOREMAN_TERMINAL_ID` |
| `foreman kanban done <id>` | Move to Done, clear claim |
| `foreman kanban block <id> --reason R` | Move to Blocked, clear claim, record reason; `--reason` is mandatory |
| `foreman kanban rm <id>` | Delete the card file, any state |
| `foreman kanban wait <id> \| --any [--timeout SECS]` | Block until the card (or, with `--any`, any card) leaves In Progress **or its claim dies** (orphan) |

- **`start` on a card with a live claim is rejected — that rejection is the
  two-agents-one-card guard.** A claim that fails the orphan check is dead,
  so `start` may seize an orphaned card.
- **`block` demands `--reason`.** A Blocked column without reasons costs the
  human an investigation per card; the flag costs the agent one argument.
- **Close-out verbs do not check the claimant.** `done`/`block` from a
  terminal other than the claimer is allowed — the same trust model as chat:
  a guardrail against confused agents, not a security boundary (any local
  process can claim any `from` on the pipe anyway). The claim check lives
  only at claim time, where the race actually matters.
- **`rm` exists because the board must not only grow.** Done cards need an
  exit: promote to a GitHub issue (`gh issue create`) or delete.
  *Rejected:* auto-deleting Done cards after a timeout (magic deletion of
  repo files); leaving deletion to hand-edits (violates single-writer).
- **`wait` gives an orchestrator a synchronous primitive.** Exit codes follow
  the house convention: `0` = card reached Done, `1` = card Blocked or
  orphaned (something needs a human), `2` = timeout or foreman unreachable —
  scripts can branch on re-dispatch vs. escalate.

### Transition rules

Enforced identically for CLI and panel writes:

- Backlog → In Progress **only via a claim** (dispatch button or `start`).
- In Progress → Done (`done`) or Blocked (`block`).
- Blocked → In Progress (re-claim via `start` or re-dispatch).
- **Release**: In Progress or Blocked → Backlog, clearing the claim — the
  panel's "send back to Backlog" action on orphaned cards.
- Done is terminal: `rm` or promote to GitHub. Anything else errors.

## Wire shape

One new request struct with an action discriminator, alongside `OpenRequest`
and friends in `src/control.rs`:

```rust
KanbanRequest {
    cmd: "kanban",
    action: String,          // "add" | "list" | "start" | "done" | "block" | "rm"
    project: Option<String>, // None = caller's FOREMAN_PROJECT_ID, else focused
    from: Option<String>,    // caller's FOREMAN_TERMINAL_ID; required for start
    id: Option<String>,
    title: Option<String>,
    body: Option<String>,
    reason: Option<String>,
    state: Option<String>,   // list filter
    json: bool,              // list output mode
}
```

- One `cmd` value with an `action` field rather than one cmd per verb: one
  new `CtrlMsg` arm, one parse site, one dispatch table entry in the server
  loop. Wire-compat v1 is satisfied additively — an old exe answers an
  unknown cmd with an error, an old CLI never sends it.
- Replies reuse `OpenReply`: list output rides the existing `history` lines
  field; `add` returns the new id in a new optional field carrying
  `skip_serializing_if` so v1 replies stay byte-identical (the same pattern
  `seq` used, per `src/control.rs` `OpenReply`).
- **`wait` is a client-side poll, not a held connection.** The pipe server
  handles one connection at a time and replies within `REPLY_TIMEOUT`
  (`src/control.rs`); a server-held blocking wait would wedge the pipe for
  every agent in the app. The CLI loops connect → `list --json` → disconnect
  → sleep (order of seconds) until the condition or the timeout.
  *Rejected:* server-side long-poll (self-inflicted denial of service on a
  serial pipe); a second notification pipe (new infrastructure for one verb).

## Dispatch from a card

The card's dispatch button is a thin wrapper over the same path `foreman
open` drives — `src/control.rs` `parse_open_args` shows the whole payload:
project, cwd, title, command vector. No parallel plumbing.

- Click dispatch on a Backlog or Blocked card → inline picker: **claude /
  codex / grok** (the set foreman already detects for tab icons and skill
  installs). *Rejected:* hardcoding one agent binary (foreman is
  multi-agent everywhere else); a persisted default-agent setting (a config
  axis for a preference that may never vary — revisit if the picker ever
  feels like friction).
- The command vector is the agent binary plus the rendered prompt as one
  positional argument; cwd is the project's cwd; the window title is the
  card title, so the tab reads as the work.
- The app records the claim and moves the card to In Progress **in the same
  action** — dispatch claims atomically, which is why a card-spawned agent
  never runs `start`.

### The prompt template

Fixed, card fields interpolated. Nothing else — no board tour; a card-spawned
agent needs exactly two commands and it gets them verbatim. Everything else
is the foreman-kanban skill's job.

```
You are a worker Session dispatched from card {id} on this project's board.

# Task: {title}

{body}

# Close-out (required)
When the work is complete, run:    foreman kanban done {id}
If you are stuck and need a human: foreman kanban block {id} --reason "<one line>"
Do not end the session without running one of these.
```

## The board window

A per-project window: a new `Content` variant in the project's nested
`WindowManager`, holding a board view. It tiles and tabs like any window, at
most one per project, toggled by a leader-key command (default binding chosen
against the live keymap at implementation time).

The chat viewer is the structural template (see `src/wm.rs` `Content` and the
chat view it carries): the view owns scroll and hover state, the card store
is shared per project, and writes drain through the same act/drain pattern
the task-manager panel uses (`docs/task-manager-panel.md` — read seam
snapshot, write seam acts).
*Rejected:* a desktop-level panel like the sessions panel — the board is
per-project data, a desktop surface would need project-switching logic and
would compete with the sessions panel for edge space.

- **Four fixed columns** (Backlog / In Progress / Blocked / Done — fence from
  the brainstorm).
- **Cards show** title, id, and a status line: the claimed terminal id while
  claimed (click jumps to the Session via the same target-surfacing path the
  panel and crew board use — `src/wm.rs` `surface_target`), an orphaned
  marker, or the blocked reason.
- **Quick-add**: a title-only input at the top of Backlog. The settled "at
  most a title-only quick-add" — taken, because creating the first card
  should not require the CLI.
- **Hover actions**, panel-style: re-dispatch and send-to-Backlog on orphaned
  cards; mark-Done and delete elsewhere. **No block button** — blocking
  demands a typed reason and v1 has no card editor, so blocking is the
  CLI's/agent's move. No drag-and-drop (fence).
- **Refresh**: repaint after own writes (single writer, no watcher needed for
  the common case), plus the directory-staleness poll from the
  Reconciliation section while the window is visible; nothing while hidden.

## Chat vs. board

Once the board exists it takes over the work-state signaling chat was
nominally for. The dividing line, so the two surfaces never compete for the
same job:

> **If it changes a card's column, it is a kanban verb. If it needs a reply
> from someone, it is chat.**

The board owns: what work exists, who has claimed what, done/blocked
signals, and orchestrator waiting (`wait`, not chat-polling). Chat keeps:
human↔agent conversation, mid-task questions ("which approach?"), and ad-hoc
coordination below the card threshold. A worker's completion signal is its
close-out verb, never a chat post. Card state is durable and validated;
chat's delivery reliability is not a dependency of the work loop.

## Vocabulary

`CONTEXT.md` gains, with the seam commit: **board** (the per-project kanban
surface), **card** (one unit of work-in-flight on it), **claim** (the
card↔Session link recorded at dispatch or `start`). "Task manager" remains
the window-switcher panel; this feature never says "task" unqualified.

## Agent education

Per the brainstorm's three tiers: the dispatch prompt embeds close-out
commands (tier 1, above); a **foreman-kanban** embedded skill covers agents
not spawned from a card (tier 2); `foreman kanban --help` is ground truth for
flags (tier 3). The skill joins the embedded set in `src/skills_install.rs`
with a `.codex/skills` twin and its openai.yaml — which means **skill edits
require an exe rebuild to propagate** (see foreman-docs-and-writing, skill
maintenance). Skill body is written at implementation time; it opens with the
same stop-sign line the dispatch and chat skills carry.

## Out of scope for v1

- Agent-state badges on cards (lands with the agent-state campaign; the
  claim's terminal id is the hook it will render on).
- Detecting "agent alive but wedged" — v1 orphan detection sees closed and
  exited terminals only. A live claude sitting on a permission prompt is the
  agent-state campaign's problem.
- Configurable columns, drag-and-drop, card editor, template system
  (brainstorm fences).
- Cross-project boards or a desktop roll-up view.
- `wait` on multiple specific ids (compose with `--any` or a shell loop).
